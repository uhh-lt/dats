# ADR 0006: A step run that cannot start or does not end

**Date:** 2026-11-13 (replaces the version of 2026-11-12)

Whatever goes wrong with a step run, the step becomes erroneous, with the pending steps after it, and Complete or Recompute retries it: a job that raises, a job whose input cannot be built (the document's fault), a job that cannot be queued because Redis is unreachable (on every start path, recompute included), and a job whose worker died. A dead worker is noticed by RQ, not by DATS: the failed hook runs as RQ's failure callback (`on_failure`), which RQ calls for a raising job and in the cleanup of a dead worker's started jobs, and which the forking worker calls for a killed job process. A failed feature activation removes its pending activation the same way.

Before, an unreachable queue never made a step erroneous, so the same outage left steps not planned, processing without a job or unchanged depending on the start path, and Restart existed to recover stranded steps (issue #887). We accept that an outage marks healthy documents as failed: the user sees it at once and recovers with the one action they already know. We also accept that a dead worker is noticed slowly (the job timeout plus up to about 18 minutes for CPU and API workers), and one gap: a process that dies between writing "processing" and queueing the job leaves the step processing without a job, which Recompute starts.
