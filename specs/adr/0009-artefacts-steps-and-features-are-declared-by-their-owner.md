# ADR 0009: Artefacts, steps and features are declared by their owner

**Date:** 2026-11-14

The central lists go: the enum `Artefact` with `CORE_ARTEFACTS` and the central table `ARTEFACT_ARCHIVE`, the enum `Feature`, and the 22 pipeline steps of `JobType`. An artefact is declared by the code that owns it with `artefact(name, always, uploaded_for, codes, archive)`, a feature with `register_feature(name, title, description, area, requires_artefacts, requires_features, default_enabled)`, and a step names its job type as text in `@register_job`. Names are text, stored in the database (step statuses, enabled features, pending computations) and never change without a data migration; a stored name of something that is no longer registered is read tolerantly and ignored, a name in a request is checked strictly (404). The checks move from the type checker to the start of the backend (`artefact_registry.check()`, `feature_registry.check()`): an artefact no step produces, a step that mixes always-computed and on-demand artefacts, a system code declared twice differently, a cycle, and too many steps stop the start. Order no longer comes from enum positions: steps are ordered by name among equals, features by area and title, enabled features are stored sorted by name.

The system codes a project needs before an artefact is produced are declared on the artefact as data (`codes=`), not as a set-up function: the set up of the artefact system creates them, the code import marks an archived code of a declared tree as a system code, a startup check compares the declarations, and the project doctor's copy is tested against them. All of these read the same trees, which a function could not offer. Deletion is not declared on the artefact: a store goes with its document through cascades, the document's files and the Elasticsearch and Weaviate deletes in `SourceDocumentService`, as before; a declared deletion would have had one implementation. Only the archive of an own store is declared, and the document archive has no open column for a new own store (deferred, O9).

Deploy: job types are pickled in Redis, so the queues and the failed registry must be empty and no upload in flight when this is deployed, and `project.artefact_computations` is reset to `{}` for every project: an entry whose job is gone keeps its features at Computing forever. An upgrade from a release before the feature toggles gets this reset from migration `457909d274d4`; an instance already past it runs `UPDATE project SET artefact_computations = '{}'` after emptying the queues.

We rejected one merged decorator for step and job (it would touch every step file once more for no new check) and a free set-up callable on the artefact (it cannot be enumerated).

Amended 2026-11-17: the storage kind is gone. "Has an archive" says that an artefact has a store of its own; the generic export of document data, metadata and annotations carries all other artefacts.
