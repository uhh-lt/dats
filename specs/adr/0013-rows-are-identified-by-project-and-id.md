# ADR 0013: Rows are identified by project and id

**Date:** 2026-11-26

The project is the tenant (#927, #928). A row of a project-owned table is identified by `(project_id, id)`, never by its id alone: **ids are unique per project, not globally**, and will not stay globally unique (an import that keeps ids, a manual repair, per-project numbering). Code that is correct only while the sequences happen to hand out globally unique ids is a bug.

1. **Schema.** Every project-owned table with an `id` has the primary key `(project_id, id)`; a table keyed by its references (link tables, `documentaspect`, `wordfrequency`, `sourcedocumentstepstatus`, `memorecent`, ...) has `project_id` first in its primary key; every unique constraint over an id column names `project_id`; every reference to a project-owned row is a composite foreign key `(project_id, x_id) -> x (project_id, id)`. There is no unique index on `id` alone.
2. **Relationships join on both columns and write only the id column.** A relationship over a composite foreign key declares `primaryjoin="and_(CodeORM.project_id == SpanAnnotationORM.project_id, CodeORM.id == foreign(SpanAnnotationORM.code_id))"`: `project_id` takes part in the join but is not `foreign()`, so SQLAlchemy loads by `(project_id, id)`, answers a many-to-one load from the identity map (`use_get`), and synchronizes only the id column. A self-reference marks the parent side with `remote()` (`and_(remote(CodeORM.project_id) == CodeORM.project_id, remote(CodeORM.id) == foreign(CodeORM.parent_id))`). Many-to-many relationships stay `viewonly` and compare `project_id` in both joins.
3. **An assignment never moves a row.** Because a relationship writes only the id column, `anno.code = code_of_another_project` keeps the annotation's `project_id`, and the composite foreign key rejects the row on flush (409). A relationship that wrote `project_id` would silently move the row into the other project.
4. **Hand-written queries join and filter with `project_id`.** A join between project-owned tables compares `project_id` and the id (or goes through the relationship attribute); a filter by ids of a project-owned table also filters by `project_id`; a CRUD method that reads or writes by id takes `project_id`.
5. **A join on a subquery of ids is enough when both sides filter the project.** A query may join a project-owned table to a subquery that selects ids only (`SourceDocumentORM.id == subquery.c.sdoc_id`, as in the annotation and document searches, the word frequencies and the timeline analysis), if the subquery and the outer query both filter the same `project_id`: then every id on both sides belongs to that project, so the id alone identifies the row.

What it costs: every relationship spells out its join; every hand-written join and every custom read carries the project; the key of the reference-keyed tables grows by one column. What it buys: tenant isolation is structural instead of a convention, explicit-id imports and per-project numbering need no change of the query layer, and many-to-one loads are answered from the identity map again (with the id-only joins of #941 they cost one SELECT per row).

`test/guards/test_same_ids_in_two_projects_crud.py` copies every row of a project into a twin project with the same ids and checks that no relationship and no CRUD read crosses projects; `test/guards/test_composite_keys.py` checks the joins, the identity map and the assignments.

We rejected a unique index on `id` alone (it would keep the old convention alive and block per-project ids), relationships that join on the id only (#941: correct only while ids are globally unique, and no identity-map lookups), and relationships that write `project_id` (`foreign_keys=[project_id, code_id]`: an assignment of an object of another project would move the row there instead of failing).
